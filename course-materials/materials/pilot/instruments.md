# Pilot Instruments

## Pre-test — Form A

Score each response 0--2 using `scoring_guide.md`.

1. Classify a passing test run, a reward score, an LLM review, and an architect's merge decision. What action does each signal permit?
2. Give one observed fact, one inference, and one validated requirement for a software change.
3. What makes an executable verifier independent of a generated candidate?
4. Why can two implementations that pass the same functional tests receive different merge decisions?
5. What information must appear in a defensible verification claim?

## Post-test — Form B

1. Candidate C-017 passes four visible tests, receives reward 0.91, and is praised by an LLM reviewer. Classify the three signals and state the strongest justified conclusion.
2. Explain how a counterexample changes the state of a candidate without automatically deciding the merge.
3. Give one mutation that can reveal a missing oracle case and explain why it is independent evidence.
4. Candidate A and B return the same values. Cite two non-functional facts that can change approval.
5. Write a property-scoped claim naming properties, environment, evidence, and remaining uncertainty.

## Learner friction survey

Rate 1 (strongly disagree) to 5 (strongly agree):

- I could run the materials without instructor repair.
- The candidate, verifier, feedback, and approval roles were distinguishable.
- I could distinguish correctness evidence, revision guidance, model opinion, and approval judgment.
- The notebook made the loop easier to understand.
- The architecture task required evidence rather than guessing the preferred answer.
- The transfer task required rebuilding domain assumptions.

Open responses:

- Which instruction or setup step was least clear?
- Which artifact most changed your initial conclusion?
- What would you remove, add, or reorder?
