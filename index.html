CENTRAL CLAIM

“Generated” is not a software-engineering completion criterion.

Completion requires independent executable evidence, a named environment, a scoped property, and a separate human decision.

Why this belongs in today’s curriculum

Four results. One emerging engineering workflow.

The module does not treat these papers as interchangeable examples. Each identifies a different failure surface and motivates a directly assessed learner action.

01 · EVALPLUS

Generation ≠ correctness

HumanEval+ expands tests by 80×. Across 26 models, stricter evaluation lowers pass@k by as much as 19.3–28.9% and can reverse rankings.

Teaching move Strengthen a weak oracle with boundaries and mutations; narrow the claim after a counterexample.

Liu et al., NeurIPS 2023
02 · SWE-AGENT

Capability depends on interfaces

An LM-oriented agent–computer interface resolves 12.47% of 2,294 SWE-bench tasks and gives a 64% relative gain over a shell-only agent on the Lite split.

Teaching move Compare bounded action and observation designs while holding the model constant.

Yang et al., NeurIPS 2024
03 · CLEVER

Specification → machine check

For 161 curated Lean tasks, specification equivalence and implementation correctness must both be proved. Current pipelines solve at most one end-to-end.

Teaching move Validate intent before implementation evidence; a checker can certify the wrong property.

Thakur et al., NeurIPS 2025
04 · RELOC

Generation becomes iterative search

Code improvement becomes drafting, neighborhood generation, candidate evaluation, and incumbent update. Revision distance guides search when test rewards are sparse.

Teaching move Record candidate states and use an explicit revise, accept, or escalate stop rule.

Lyu et al., NeurIPS 2025

The technical concept

A verifier-guided agent loop learners can inspect.

The oracle is independent when it is not copied from the candidate or accepted from the model’s explanation. Passing supports only the named property in the named environment.

What this resource contributes

Not a fifth algorithm—a teachable integration.

We connect oracle adequacy, interface design, specification fidelity, and search policy in one evidence-producing software-engineering workflow.

  1. 01
    One bounded concept

    A consistent candidate–verifier–feedback–revision vocabulary across testing, architecture, and authorization.

  2. 02
    Observable learning

    Evidence ledgers, counterexamples, diffs, and decision records replace prompt fluency as assessment evidence.

  3. 03
    Assurance boundaries

    Learners see why passing functionality does not settle intent, architecture, security, or approval.

  4. 04
    Reproducible access

    A prepared candidate produces the central result without model access, API cost, or network variability.

Core workshop · 150 minutes

From intent to defensible change.

00–20

Problem → specification

Separate stakeholder intent, executable property, and acceptance decision.

20–55

Candidate + weak oracle

Run a provenance-marked patch and resist equating a green suite with correctness.

55–90

Counterexample + revision

Add boundary and mutation cases, preserve evidence, and revise the candidate.

90–120

Architecture + governance

Compare test-equivalent implementations under architecture and security constraints.

120–150

Authorization transfer

Design a new verifier for a non-isomorphic document-access task.

Reproducibility and review

Every claim leaves an inspectable artifact.

TEACH

Slides + instructor guide

A timed sequence, facilitation notes, misconceptions, and spoiler separation.

EXECUTE

Notebook + exercise repos

Prepared candidate, weak and stronger suites, architecture comparison, and transfer task.

ASSESS

Rubrics + evidence ledger

Anchored pre/post items, claim-calibration rubric, decision record, and verification checklist.

REPRODUCE

One-command build

Tests exercises, executes the notebook, rebuilds paper and deck, and produces licensed packages.

Claim boundary

The package is pilot-ready. It does not claim human learning outcomes without participant data. A passing verifier supports explicit properties only; human approval remains a separate lifecycle gate.
